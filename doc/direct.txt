==============================================================================
1. Intro                                                      *direct.vim-intro*

Load a directory into a buffer with each root-level line corresponding to a file
or subdirectory. Edit those root rows to create, rename, or delete filesystem
entries. Directories can also be expanded for browsing; their child rows are
materialized in the buffer and removed when collapsed.

    - navigate around the filesystem easily
    - rename, create and delete files and directories
    - yank and paste files and directories
    - full undo and redo history for every filesystem change

Filename highlights ~

Visible directories use DirectDirectory (default link Directory) at any
indentation depth. Hidden directories and files use their Comment defaults.
When icons are enabled, hidden directory and file icons also use the Comment
style; visible directory and file icons retain their Directory and Normal
defaults. These highlight groups can be customized in a colorscheme or with
`nvim_set_hl()`:

    DirectDirectory             visible directory names (Directory)
    DirectHiddenDirectory       hidden directory names (Comment)
    DirectHiddenFile            hidden file names (Comment)
    DirectFolderIcon            visible folder icons (Directory)
    DirectFileIcon              file icons (Normal)
    DirectHiddenFolderIcon      hidden folder icons (Comment)
    DirectHiddenFileIcon        hidden file icons (Comment)
    DirectGitAddedIcon          added status icon (DiffAdd)
    DirectGitAdded              added status name (DiffAdd)
    DirectGitModifiedIcon       modified status icon (DiffChange)
    DirectGitModified           modified status name (DiffChange)
    DirectGitRenamedIcon        renamed status icon (DiffChange)
    DirectGitRenamed            renamed status name (DiffChange)
    DirectGitConflictedIcon     conflicted status icon (ErrorMsg)
    DirectGitConflicted         conflicted status name (ErrorMsg)
    DirectGitStagedIcon         staged icon color (DiffAdd)
    DirectGitStaged             staged filename color (DiffAdd)
    DirectGitStagedGutter       staged gutter color (DiffAdd)
    DirectGitUnstagedIcon       unstaged icon color (DiffChange)
    DirectGitUnstaged           unstaged filename color (DiffChange)
    DirectGitUnstagedGutter     unstaged gutter color (DiffChange)

Defaults are reapplied after a ColorScheme event without replacing
user-defined groups. Listing files receive no filename-, filetype-, or
special-name-derived highlights; Git status styling is described below.

Direct loads its listing syntax locally, including when Neovim's global syntax
loader is disabled.

2. Requirements                                        *direct.vim-requirements*

    - Neovim >= 0.12
    - No Python: the plugin is pure Lua. Git is optional for ordinary listings;
      Git status and `respect_gitignore` use the Git command-line executable.

Run `:checkhealth direct` to confirm the version and the data home in use:

    :checkhealth direct

3. Setup                                                    *direct.vim-setup*

`setup()` is optional; the defaults apply when it is never called.

    require('direct').setup({
      map_default_keys = true, -- set false to install no default mappings
      show_hidden = true, -- set false to hide dot-prefixed entries
      respect_gitignore = false, -- opt in to Git ignore filtering
      show_folder_icons = false, -- opt in to Nerd Font folder icons
      show_file_icons = false, -- opt in to a generic Nerd Font file icon
      icons = {
        file = '\u{f0214}',
        folder = '\u{f024b}',
        folder_open = '\u{f0770}',
      },
      max_recursive_expand_depth = false, -- false means unlimited
      git = { enabled = true, display = 'gutter' }, -- gutter, icon, text, or both
    })

`setup()` is idempotent, may be called more than once, and reports an unknown
option name as an error instead of silently ignoring it. See
|direct.vim-mappings| for `map_default_keys`.

`max_recursive_expand_depth` defaults to `false` (unlimited). Set it to a
positive integer to cap the directory levels opened by recursive commands
`zO`, `zA`, `zR`, and `:DirectUnfoldAll`. The cap does not restrict one-level
`zo`/`za` browsing.

Dot-prefixed files and directories are visible by default. Set
`show_hidden = false` to hide them. `:DirectToggleHidden` (also mapped to `gh`)
switches the current direct buffer's view. It refuses while the listing has
unsaved edits, refreshes from disk, and collapses expanded subtrees so every
visible level uses the same filter.

In a direct listing, `gs` (or `:DirectToggleGitStatus`) toggles a view showing
only entries with a Git status. Directories with changed descendants are
included, and expanding them applies the same filter to their children. It
refuses while the listing has unsaved edits. Outside a Git repository, or when
`git.enabled = false`, the filtered view is empty. Entries hidden by this view
are not treated as deletion sources during sync.

File and folder icons ~

Set `show_folder_icons = true` to display inline directory glyphs, and
`show_file_icons = true` to display one generic icon for every file; both options
default to `false`. Built-in glyphs require a Nerd Font. Customize them with the
`icons` table: `file` defaults to U+F0214, `folder` to U+F024B, and `folder_open`
to U+F0770. These glyphs are used regardless of filetype. When only one kind of
icon is enabled, the other kind reserves a blank icon slot so entry names stay
aligned. Icons are virtual text, so buffer lines and filesystem behavior are
unchanged. No icon plugin or other dependency is required.
With folder icons enabled, click a folder icon to expand or collapse that
directory in place. Mouse input must be enabled in Neovim (for example,
`:set mouse=a`). Clicking elsewhere in the listing retains normal cursor
placement.

Git status ~

In a Git repository, direct reads status once per listing refresh. Added
(including untracked), modified, Git-detected renamed, and conflicted entries
are styled without changing listing text. Directories inherit the strongest
status of changed descendants, in the order conflicted, renamed, added, then
modified. The default gutter uses `┃` for unstaged changes (including untracked
files) and `┃•` for staged changes. Mixed files and mixed folders with staged
descendants use the staged display by default; `mixed_file` and `mixed_folder`
can be configured independently. Conflicts are identified by their conflict
styling instead. Deleted entries have no listing row to mark. Re-list to refresh
Git status.

Press `gs` or run `:DirectToggleGitStatus` to show only entries with a status;
press it again to restore the normal listing. This filter composes with hidden,
wildignore, and Git-ignore filtering. Entries it hides are not treated as
deletion sources during sync. In directories with changed descendants, the
directory remains visible and its expanded children use the same filter.

By default, `git.display` is `gutter`: changed entries show a `┃` in the sign
column without changing their icon glyphs or highlighting their names. Added
entries use DiffAdd, modified and renamed entries use DiffChange, and conflicts
use ErrorMsg. Choose `icon`, `text`, or `both` to select inline icon and/or name
highlighting; gutter symbols remain configurable per status. Icon and entry-name
highlighting are unset by default; set `icon_hl` and/or `text_hl` per status to
opt in. Configure highlight groups, optional icon overrides, and gutter symbols
per status:

    require('direct').setup({
      git = {
        display = 'both',
        staging = {
          enabled = true,
          staged = {
            icon_hl = 'MyStagedIcon',
            text_hl = 'MyStagedText',
            icon = { file = '+' },
            gutter = { symbol = '┃•', highlight = 'MyStagedGutter' },
          },
          unstaged = {
            icon_hl = 'MyUnstagedIcon',
            text_hl = 'MyUnstagedText',
            gutter = { symbol = '┃', highlight = 'MyUnstagedGutter' },
          },
          mixed_file = {
            icon_hl = 'MyMixedFileIcon',
            text_hl = 'MyMixedFileText',
            icon = { file = '±' },
            gutter = { symbol = 'F', highlight = 'MyMixedFileGutter' },
          },
          mixed_folder = {
            icon_hl = 'MyMixedFolderIcon',
            text_hl = 'MyMixedFolderText',
            icon = { folder = '±', folder_open = '±' },
            gutter = { symbol = 'D', highlight = 'MyMixedFolderGutter' },
          },
        },
        statuses = {
          added = {
            icon_hl = 'MyGitAddedIcon',
            text_hl = 'MyGitAdded',
            icon = { file = '+', folder = '+', folder_open = '+' },
            gutter = { symbol = 'A', highlight = 'MyGitAddedGutter' },
          },
          modified = {
            icon_hl = 'MyGitModifiedIcon',
            text_hl = 'MyGitModified',
          },
        },
      },
    })

Icon overrides are optional; unspecified file/folder variants keep their base
`icons` glyphs. Gutter symbols default to `┃` and can be disabled per status with
`gutter = false`. Set `git.enabled = false` to disable Git status display; this
does not affect Git-ignore filtering. Mixed-file and mixed-folder settings
inherit the staged settings by default and can independently override
`icon_hl`, `text_hl`, `icon`, and `gutter`. Set `git.staging.enabled = false`
to disable staging-specific styling while retaining regular status display.

Git-ignore filtering is separately opt-in with `respect_gitignore = true`. It
uses Git's own matching for root and nested `.gitignore` files, negations,
anchoring, escaped patterns, `.git/info/exclude`, and the configured global
excludes file. Tracked files remain visible, as do directories containing
tracked descendants. Outside a repository this filter has no effect. Git must
be available when the option is enabled; if an ignore query fails in a detected
repository, listing fails safely instead of guessing. If effective ignore rules,
excludes, or tracked index membership change after listing, sync refuses before
filesystem or history effects; re-list to refresh the rule snapshot. The
fingerprint is deliberately conservative: it currently walks the full repository
to find ignore sources, so large trees incur a full-tree scan when listing or
validating sync. A change to a nested repository's ignore source may require a
re-list even when that source did not affect the current view.

4. Navigate                                              *direct.vim-navigate*

In normal mode, `-` lists the directory of the current file, or the working
directory when the buffer is not tied to one (a buffer with no file name, or a
non-empty `&buftype` such as a direct listing). You can also open a directory
with `:edit foo/`, or by starting Neovim on it.

Once a directory is listed, `-` goes up to its parent directory and `<Enter>`
opens the entry under the cursor: a directory line opens a new listing, a file
line opens the file. Double-clicking an entry opens it the same way. This is
enough to move around the filesystem without remembering any extra command.

Use `zo` or `za` on a directory to expand it in place. Children are read lazily,
one level at a time; repeating an expansion does not re-read or duplicate them.
`zO` or `zA` recursively expands a directory, and `zC` recursively collapses
it. `zR` expands all root directories and `zM` collapses them all. Recursive
opening respects |direct.vim-setup|'s `max_recursive_expand_depth`; the initial
listing remains flat.

5. Edit                                                      *direct.vim-edit*

When viewing a directory, edit its listing as if you were editing a file, using
any Vim command (`di`, `o`, `:s`, macros, and so on). Saving synchronises the
changes with the filesystem and then re-lists the directory.

At the root level, a save is classified as exactly one of rename, create or
delete:

    - Rename: edit the line of the file or directory you want to rename, and
      save.
    - Create: add new lines at any location, and save. A new relative path such
      as `reports/2026/summary.txt` creates the file and missing parent
      directories. A path ending in `/`, such as `reports/2026/`, creates a
      directory at that path. After saving nested paths, their parent
      directories are expanded and the cursor moves to the last added entry.
    - Delete: delete the lines for the entries you want to remove, and save.
      Deleted entries are yanked automatically, so you can paste them back.

The trailing-slash rule ~

A directory must always be written with a trailing slash, and a file must never
have one: the line, not the filesystem, decides what will be created or
renamed. Renaming `foo/` to `foo` therefore replaces the directory `foo` with a
file, and adding a line `bar` creates a file while `bar/` creates a directory.

At the root level, an edit that both adds and deletes entries, or that leaves a
duplicated line, is reported as ambiguous, naming both sides of the comparison.
Nothing is changed, no history is written, and the buffer stays modified so you
can fix it.

`&wildignore`, dot-hidden visibility, Git-ignore filtering, and the `gs`
Git-status-only view are independent; entries hidden by any active filter are
omitted. `&wildignore` keeps its existing behavior.
Each directory captures the filters and matches used for that listing. Changing
an option does not change an existing listing's sync rules; re-list to refresh
them. Filtered entries are excluded from sync, and sync is refused before
filesystem or history effects if an add/rename would use an occupied filtered
path or a directory move would carry a filtered descendant. Newly appearing
entries matching the captured filters are not treated as delete sources.
Directory symlinks are treated as leaves when renamed; their targets are not
scanned or moved.

Expanded rows ~

Every expanded directory is an independent edit scope. Edit, add, or delete its
children just as at the root. Directory lines end in `/`; files do not. Changes
in multiple expanded directories are combined during one sync, and deleted
entries are auto-yanked before removal.

Indentation defines parentage: root rows have no leading spaces, direct children
have two spaces, and each additional level adds two more. A child must be under a
directory. Change a row's indentation or move it beneath another expanded
directory to move it; the entry and its contents are preserved. New rows may be
nested under a directory created in the same edit. Directory renames and moves
carry their contents and retain visible expansions when possible.

Before syncing an edited subtree, direct verifies that its directory contents
have not changed on disk since expansion. Invalid indentation, missing parents,
duplicate destinations, lost identities, or a stale snapshot refuse the whole
sync before auto-yank, filesystem, or history effects. A whole-line replacement
whose identity is lost is paired as a rename only when sibling identities make
that pairing unambiguous; otherwise the save is refused. Root-level edits retain
the existing rename/create/delete classifier and ambiguity rules.

Deleting a directory row removes and auto-yanks its whole tree, including
materialized descendants, unless you reindent surviving rows under another
directory in the same edit to move them out first. Moving or renaming a directory
together with separate edits to its descendants must be saved in separate syncs
when their filesystem action order would otherwise be ambiguous. Expansion and
collapse remain ordinary text-undo changes. `:undo` after collapse restores child
rows and identities; `:redo` re-applies the collapse. Redo restores materialized
identities only when the original undo sequence and exact directory snapshot
still match. A changed or ambiguous snapshot remains unsafe to save, open, or yank.
Path components beginning with whitespace and paths that could escape the listed
directory (absolute paths, empty components such as `a//b`, or `.`/`..` components
such as `a/../b`) are refused at save time. Nested paths are supported for new
entries only; renames remain single-component names. Newly created parent
directories are recorded separately, so `u` and `<C-r>` can undo and redo them
in the correct order.

Windows-specific component checks reject backslashes, drive prefixes, reserved
device names (including extension aliases), and trailing dots or spaces that
Win32 would normalize. Native Windows filesystem traversal has not been
verified; this documentation does not claim Windows support.

6. Undo / Redo                                                 *direct.vim-undo*

In a direct buffer, `u` and `<C-r>` undo and redo the last filesystem action
performed by Direct, such as a sync or paste. They invoke the same actions as
`:DirectUndo` and `:DirectRedo`.

Use `:undo` and `:redo` for Neovim text undo and redo in the listing. Text undo
only changes buffer lines; it does not rename, create, delete, or restore
anything on disk.

==============================================================================
7. Yank / Paste                                                *direct.vim-yank*

`yy` and `Y` yank the file or directory on the current line, and a visual `y`
yanks the selected range. `p` and `P` paste into the directory under the cursor,
or into a file's parent directory when the cursor is on a file. Entries inside
expanded directories use their displayed directory, too. Directories are yanked
recursively, so you can copy directory trees around the filesystem.

If an entry with the same name already exists, you are prompted
(`File already exists. Paste as: `, or `Directory ...`) and can paste it under
another name. An empty answer skips that entry and leaves the original
untouched.

Yank, paste, undo and redo all work on the filesystem through the same history,
so `:DirectUndo` reverses a paste as well.

Undoing a paste verifies every pasted file, exact directory tree, or symlink
target against the current register copy before changing anything. A missing,
changed, unreadable, or re-yanked register refuses the entire Unpaste and keeps
the history entry. Matching entries are atomically captured to unique
same-directory `.direct-unpaste-*` paths and rechecked before deletion. If
capture fails, Direct restores what it can with no-replace; a blocked quarantine
is preserved and reported for manual recovery. Deletion uses only captured
quarantine paths, never the original paste name, so a new object appearing at
that name is not removed. A crash or failure during deletion can leave
quarantine debris. Identical-content replacements are indistinguishable from
the original paste; open handles and competing same-user processes can still
race checks because there is no filesystem snapshot or inter-process lock.

Paste name clashes use Neovim's callback-based `vim.ui.input`; there is no
synchronous prompt fallback. Cancel, an empty answer, or an invalid basename
skips that entry. A still-colliding answer is retried up to ten times. Entries
copied before a later skip or error are retained and recorded; if all entries
are skipped, no history action or success notice is produced. While a prompt is
pending, sync, paste, undo, and redo are refused. History writes and listing
refresh wait until the callback flow completes. Grouped moves retain their
existing synchronous staging behavior.

8. Commands                                                *direct.vim-commands*

    :DirectList {dir}
        List {dir} in a direct buffer. {dir} completes as a directory.

    :DirectListBuffer
        List the directory of the current file, or the working directory when
        the buffer is not tied to one (no file name, or a non-empty
        `&buftype`).

    :DirectListCwd
        List the current working directory.

    :DirectSync
        Classify and apply the edits in the current buffer. Also runs on
        `:write` (`BufWriteCmd`).

    :DirectFoldAll
        Collapse all expanded directories in the current listing.

    :DirectUnfoldAll
        Recursively expand all directories in the current listing.

    :DirectToggleHidden
        Toggle dot-hidden entries in the current direct listing and refresh its
        view. Refuses if the listing has unsaved edits.

    :DirectToggleGitStatus
        Toggle the Git-status-only view in the current direct listing. Refuses
        if the listing has unsaved edits.

    :DirectUndo
        Undo the last filesystem action.

    :DirectRedo
        Redo the last undone action.

    :DirectYank
        Yank the selected entries (a range; the default is the current line).

    :DirectPaste [dir]
        With no argument, paste into the directory under the cursor (or a file's
        parent directory) and refresh the listing. With {dir}, paste into {dir}
        and leave the current buffer untouched.

    :DirectPasteAs {name}
        Paste into the cursor row's directory (or a file's parent directory) as
        {name}.

    :DirectRun {command}
        Run {command} asynchronously in the shell, with the listing directory
        as the working directory. Each literal {} is replaced by the
        shell-escaped absolute path of the current entry; leave {} unquoted.
        The command must contain {} and the current row must name an existing
        entry. Captured output and exit status are reported when it finishes.

`:DirectSync`, `:DirectFoldAll`, `:DirectUnfoldAll`,
`open()` (the public API used by the entry mappings),
    :DirectGit {command}
        Run {command} like :DirectRun, then refresh Git status decorations in
        the originating loaded listing when it completes. It does not re-list
        or change buffer text.
`:DirectUndo`, `:DirectRedo`, `:DirectYank`, `:DirectPaste` (no argument),
`:DirectPasteAs`, `:DirectRun`, and `:DirectGit` report an error and do nothing
when the current buffer is not a direct buffer. `:DirectRun` does not refresh Git
status; use `:DirectGit` when status decorations should refresh after completion.
The listing commands `:DirectList`, `:DirectListBuffer` and
`:DirectListCwd` remain available from ordinary buffers; they list a directory
without operating on the current buffer's listing. `:DirectPaste {dir}` is also
available from an ordinary buffer: it pastes into the explicitly named
directory and never touches the current buffer.

9. Mappings                                                *direct.vim-mappings*

Global (normal mode), installed when `map_default_keys` is true:

    -           :DirectListBuffer~

Buffer-local, in a direct buffer (all mappings follow `map_default_keys`):

    Mode        Key         Action ~
    normal      <CR>        open the entry under the cursor
    normal      zo          lazily expand one directory level
    normal      za          expand or collapse one directory
    normal      zc          collapse one directory
    normal      zO          recursively expand a directory
    normal      zA          recursively expand or collapse a directory
    normal      zC          recursively collapse a directory
    normal      zR          recursively expand all root directories
    normal      zM          collapse all root directories
    normal      -           open ../ (the parent directory)
    normal      u           undo the last filesystem action
    normal      <C-r>       redo the last filesystem action
    normal      yy, Y       :DirectYank (current line)
    visual      y           :DirectYank (selected range)
    normal      p, P        :DirectPaste
    normal      gh          :DirectToggleHidden
    normal      ga          :DirectGit git add -- {}
    normal      gr          :DirectGit git reset -- {}
    normal      gc          :DirectGit git checkout -- {}
    normal      gs          :DirectToggleGitStatus

The buffer-local `-` wins over the global `-` inside a direct buffer. All
buffer-local mappings, including fold and mouse mappings, are omitted when
`map_default_keys` is false.
`:DirectUnfoldAll` and `:DirectFoldAll` provide command-line equivalents of `zR`
and `zM`.

10. Data directory                                          *direct.vim-data*

State has no cache and is resolved on every use:

    1. $XDG_DATA_HOME/direct when $XDG_DATA_HOME is set and non-empty;
    2. otherwise $HOME/.local/share/direct (falling back to Neovim's standard
       data directory, with a warning, when neither variable is set).

Run `:checkhealth direct` to print the resolved data home. Inside it:

    history/    undo.log and redo.log, the filesystem undo/redo history
    trash/      removed entries, kept so an undo can restore them
    register/   the most recent yank, and its content pointer

    Undo and redo use JSONL. Each stack begins with the exact header
    {"format":"direct-history","version":1}, followed by one canonical JSON
    action record per line. Paste/unpaste names are JSON arrays. Before reading
    the register or changing the filesystem, direct validates path inputs and
    classifies both history files from raw bytes. Invalid UTF-8, control
    characters, malformed JSON, and unknown history formats are refused without
    changing history, the register, or the filesystem.

    Recognized Python-era tab logs and Lua v2/v3 logs are reset to empty
    current-format history with a warning. They are never replayed or migrated,
    and no backup is created. Unknown, future, malformed, unreadable, and
    pre-2018 space-framed logs are preserved byte-for-byte and block the
    triggering operation.

    Each history-file rewrite uses an exclusive same-directory temporary file,
    flushes and closes it, then atomically renames it over the owned log. This
    does not make the full pop -> filesystem action -> append sequence atomic:
    a crash between those steps can leave the log and filesystem out of sync.
    There is no multi-operation journal or inter-process lock.

    Filesystem destinations use atomic no-replace placement. Darwin and Linux
    use their native exclusive-rename primitive; unsupported platforms or
    filesystems fail closed. Touch uses exclusive file creation, and mkdir
    refuses an existing destination. Cross-device moves copy files to an
    exclusive temporary file and directories to a private temporary tree in the
    destination parent before no-replace placement. Symlinks are recreated, not
    followed; FIFO, socket, and device sources are refused. If placement
    commits but source removal fails, both paths are reported and the destination
    is recorded; two copies may remain. Network filesystems and unsupported
    filesystem semantics are not guaranteed. Before removing an EXDEV source,
    direct atomically captures it in a private temporary directory beside the
    source and compares copied file bytes or recursive directory contents and
    symlink targets. If they differ or cannot be verified, direct restores the
    source with no-replace or preserves and reports its temporary path. A crash
    in this brief capture/verify/remove window can leave a
    `.direct-exdev-source-*` recovery directory. Concurrent writers can still
    change open files after comparison; there is no snapshot or inter-process
    lock. The final destination rename is atomic no-replace, but source/temp
    inode checks and cleanup remain pathname operations. A same-user process can
    race a replacement after a check; in that narrow window direct may preserve
    and report a stranded temp or quarantine path for manual recovery.

11. Upgrading from the Python version                       *direct.vim-upgrade*

The Lua rewrite uses a new on-disk format and does not migrate the Python-era
data:

    - History: recognized Python-era tab logs and Lua v2/v3 logs are discarded
      and reset to empty JSONL history with a warning and no backup. They are
      never replayed or migrated, so their undo history does not survive. Old
      space-framed Python logs and any unknown, malformed, or unreadable log are
      preserved byte-for-byte and block the triggering operation.
    - Register: entries written by the Python version are still listed. Names
      with spaces are supported by the JSONL format; names with control
      characters or invalid UTF-8 are skipped with an error.
    - Trash: Python-era trash entries are still read, so an entry removed
      before the upgrade can still be restored.
