1. Introduction                                             *direct.vim-intro*

direct.vim lists a directory in a buffer, one line per entry. Rename, create,
delete and move files with ordinary Vim editing, then |:write| to apply the
changes to the filesystem.
>
    src/
      components/
        button.lua
      init.lua
    docs/
    README.md
<
Features:

    - Edit with any Vim command: |cw|, |dd|, |o|, |:s|, macros, and so on.
    - Expand directories in place with the usual fold keys, and move entries
      by changing their indentation.
    - Undo and redo every filesystem change with |u| and |CTRL-R|. The
      history is kept on disk.
    - Yank and paste files and whole directory trees.
    - See Git status, filter to changed files, stage and restore entries, and
      hide Git-ignored files.
    - Language servers are told about renames, creates and deletes.

direct.vim is pure Lua and replaces |netrw| for directory buffers.

==============================================================================
2. Requirements                                      *direct.vim-requirements*

    - Neovim 0.12 or later.
    - Git, for Git status and Git-ignore filtering (optional). Ignore
      filtering is on by default; see |direct-respect_gitignore|.
    - A Nerd Font with the Font Awesome glyphs, for the default icons
      (optional). See |direct-icons|.
    - nvim-web-devicons, for icons that match each file's type (optional).
      See |direct-show_filetype_icons|.

No Python is needed. To check the Neovim version and the
data directory in use, run:
>
    :checkhealth direct
<

3. Quick start                                         *direct.vim-quickstart*

1. Open a directory. Any of these work:
>
    nvim .
    :edit some/dir/
    :DirectList some/dir
<
   Or press `-` in any buffer to list the directory of the current file.

2. Move around. <CR> opens the entry under the cursor and `-` goes up to the
   parent directory. `zo` expands a directory in place.

3. Edit the listing, then save with |:write|:

    To...       Do this ~
    Rename      Change a name, e.g. `old.txt` to `new.txt`.
    Create      Add a line, e.g. `notes.md` or `reports/2026/summary.md`.
    Delete      Delete the line. The entry is yanked, so `p` puts it back.
    Move        Re-indent the line under another expanded directory.

4. Press `u` to undo the filesystem change.

Directory names end with the separator (`archive/`); file names do not. At the
root level, save one kind of change at a time. If direct.vim can't tell what
you meant, the save is refused and nothing on disk changes. See
|direct.vim-edit| for the full rules.

4. Navigating                                            *direct.vim-navigate*

Opening a listing ~

In normal mode, `-` lists the directory of the current file. In a buffer with
no file name, or with a non-empty 'buftype', it lists the working directory
instead. You can also open a directory with `:edit foo/` or by starting Neovim
on it.

Moving between directories ~

In a listing:

    <CR>        Open the entry under the cursor. A directory opens a new
                listing and a file opens the file. Double-clicking an entry
                does the same.
    -           Go up to the parent directory.
    z-          Go up to the parent directory and expand the directory you
                came from.

Expanding directories ~

Directories can be expanded in place, so the listing becomes a tree. The
initial listing is always flat.

    zo          Expand one directory level.
    za          Expand or collapse one directory.
    zc          Collapse one directory.
    zO          Expand a directory recursively.
    zA          Expand or collapse a directory recursively.
    zC          Collapse a directory recursively.
    zR          Expand all directories (|:DirectUnfoldAll|).
    zM          Collapse all directories (|:DirectFoldAll|).

Children are read lazily, one level at a time. Expanding an already expanded
directory does not re-read or duplicate its children. Collapsing removes the
child rows from the buffer, and expanding again re-reads the directory.

Recursive expansion (`zO`, `zA`, `zR` and |:DirectUnfoldAll|) is unlimited by
default. Set |direct-max_recursive_expand_depth| to cap it. The cap does not
affect one-level `zo` and `za`.

With folder icons enabled and mouse input on (for example `:set mouse=a`),
clicking a folder icon expands or collapses that directory. Clicking elsewhere
places the cursor as usual.

Jumping ~

    ]d  [d      Next or previous directory row, including directories inside
                expanded subtrees. Collapsed descendants are skipped, and the
                expansion state does not change.
    ]f  [f      Next or previous file row, skipping directories. Files
                inside expanded subtrees count; collapsed or hidden entries
                don't, and it stops at the ends rather than wrapping.
    ]c  [c      Next or previous entry with a Git change. See
                |direct.vim-git-navigate|.

5. Editing                                                   *direct.vim-edit*

Edit a listing as you would any file, using any Vim command. When you save,
direct.vim compares the buffer with the filesystem, applies the differences,
and lists the directory again.

Rename, create and delete ~
                                                         *direct.vim-classify*
At the root level, each save is classified as exactly one of these:

    Rename      Change the text of an existing line.
    Create      Add new lines anywhere.
    Delete      Delete lines. Deleted entries are yanked first, so you can
                paste them back with `p`.

An edit that both adds and deletes root rows, or that leaves a duplicated
line, is ambiguous. The error names both sides of the comparison. Nothing is
changed, no history is written, and the buffer stays modified so you can fix
it.

Directories and files ~
                                                   *direct.vim-separator-rule*
A directory is always written with a trailing separator, and a file never has
one. The line decides what is created or renamed, not the filesystem:

    - Adding `bar` creates a file, and adding `bar/` creates a directory.
    - Renaming the directory `foo/` to `foo` replaces it with a file.

The separator is the platform's filesystem separator by default. Set
|direct-directory_separator| to `/` or `\` to choose a different one. The
separator is reserved inside entry names, so an entry whose name contains it
is left out of the editable listing.

Creating nested paths ~

A new line can contain a relative path, such as `reports/2026/summary.txt`.
direct.vim creates the file and any missing parent directories. A path ending
in the separator, such as `reports/2026/`, creates a directory. After the
save, the new parent directories are expanded and the cursor moves to the last
added entry. Parent directories are recorded separately in the history, so `u`
and `<C-r>` undo and redo them in the right order.

Nested paths are only for new entries. A rename changes a single name.

These are refused when you save:

    - Absolute paths.
    - Empty components, such as `a//b`.
    - `.` or `..` components, such as `a/../b`.
    - Components that begin with whitespace.

Editing expanded directories ~
                                                        *direct.vim-tree-edit*
Each expanded directory is its own edit scope. Edit, add or delete its
children just as you would at the root. Changes in several expanded
directories are combined into one save.

Indentation defines the tree. Root rows have no indentation, and each level
adds |direct-indent_size| spaces (2 by default). Every child must sit under a
directory.

To move an entry, change its indentation or move its line beneath another
expanded directory. The entry keeps its contents. New rows can be nested under
a directory created in the same edit. Renamed and moved directories carry
their contents and keep their visible expansions where possible.

Deleting a directory row deletes its whole tree, including expanded
descendants, and yanks it first. To keep some of the descendants, re-indent
them under another directory in the same edit.

If you move or rename a directory and also edit its descendants, you may need
to save the two changes separately. direct.vim refuses the save when it can't
determine a safe order for the filesystem actions.

When a whole line is replaced, direct.vim treats it as a rename only when the
surrounding entries make the pairing unambiguous. Otherwise the save is
refused. Root-level edits always follow the rename/create/delete rules above.

What gets checked before a save ~

Before changing anything, direct.vim checks the whole edit. Any of the
following refuses the entire save. Nothing is yanked, changed on disk or
written to history:

    - Invalid indentation, or a child without a parent directory.
    - Two rows with the same destination.
    - A row whose original entry can no longer be identified.
    - An expanded directory whose contents changed on disk since it was
      listed.
    - A filter change that affects the save. See |direct.vim-filters|.

Text undo of expansions ~

Expanding and collapsing are ordinary text changes, so |:undo| after a
collapse restores the child rows, and |:redo| collapses again. Redo can only
restore entry identities when the undo sequence and the directory contents are
exactly as they were. If they aren't, those rows are treated as unsafe to
save, open or yank.

Filters ~
                                                          *direct.vim-filters*
Four independent filters can hide entries from a listing:

    - 'wildignore'.
    - Dotfiles, when |direct-show_hidden| is off (toggle with `gh`).
    - Git-ignored entries, when |direct-respect_gitignore| is on (toggle with
      `gi`).
    - The Git-status-only view (toggle with `gs`).

Hidden entries are left out of the save. They are never treated as deleted,
including entries that appear on disk later and match the filters.

Each listing records the filters it was made with. Changing an option doesn't
affect an existing listing; list the directory again to apply it.

A save is refused if it would:

    - Create or rename to a path occupied by a hidden entry.
    - Move a directory that contains a hidden entry, or an entry the listing
      can't show, such as a dangling symlink or a FIFO.

Directory-only 'wildignore' patterns such as `cache/` also protect matching
nested directories. Directory symlinks are treated as single entries: renaming
one does not scan or move its target.

Windows ~

Names are checked against Windows rules: backslashes, drive prefixes, reserved
device names (including with extensions), and trailing dots or spaces are
rejected. Native Windows filesystem traversal has not been verified, and
Windows is not officially supported.

6. Undo and redo                                             *direct.vim-undo*

In a listing, `u` and `<C-r>` undo and redo the last filesystem action, such
as a save or a paste. They are the same as |:DirectUndo| and |:DirectRedo|.

The history is stored on disk, so it survives restarting Neovim and is shared
by every listing. See |direct.vim-data|.

Use |:undo| and |:redo| to undo text changes in the listing. Text undo only
changes buffer lines; it never renames, creates, deletes or restores anything
on disk.

7. Yank and paste                                            *direct.vim-yank*

Yanking ~

`yy` and `Y` yank the entry on the current line, and `y` in Visual mode yanks
the selected lines. Directories are yanked with all their contents. Entries
inside expanded directories can be yanked too.

The yank is copied into direct.vim's own register in the data directory, so it
is shared between Neovim instances. It is separate from Vim's registers.

Pasting ~

`p` and `P` paste into the directory under the cursor. On a file, they paste
into the file's directory. |:DirectPaste| with a directory argument pastes
there from any buffer, and |:DirectPasteAs| pastes under a new name.

If an entry with the same name already exists, you are prompted for another
name ("File already exists. Paste as:"). The prompt uses |vim.ui.input()|.
Cancelling, giving an empty answer or giving an invalid name skips that entry.
A name that still clashes is asked again, up to ten times. While a prompt is
open, saves, pastes, undo and redo are refused.

Entries pasted before a later one is skipped or fails are kept and recorded in
the history. If every entry is skipped, nothing is recorded.

Undoing a paste ~
                                                          *direct.vim-unpaste*
Pastes are in the undo history like any other change. Before removing
anything, undo checks every pasted file, directory tree and symlink against
the register. If any of them is missing, changed or unreadable, or the
register has been replaced by a newer yank, the whole undo is refused and the
history entry is kept.

Matching entries are first moved to `.direct-unpaste-*` paths in the same
directory and checked again. Only those captured paths are deleted, so a new
file created under the original name is never removed. If the capture fails,
direct.vim restores what it captured without overwriting anything. A
quarantine path it can't restore is kept and reported so you can recover it.

Limits: a crash during deletion can leave `.direct-unpaste-*` paths behind. A
replacement with identical contents can't be told apart from the original
paste. Another process that has the files open can still change them between
the check and the deletion.

8. Git                                                        *direct.vim-git*

In a Git repository, direct.vim shows the status of each entry and offers a
few Git shortcuts. Turn the status display off with |direct-git.enabled|.
Ignore filtering is controlled separately by |direct-respect_gitignore|.

Status display ~
                                                       *direct.vim-git-status*
Git status is read once each time a listing is refreshed. To update it, list
the directory again, or use |:DirectGit|, which refreshes it for you.

Each row shows a two-slot status component, right-aligned at the edge of the
window. The first slot is the index (staged) status and the second is the
worktree status. It is virtual text, so it doesn't change the buffer lines.
Very long rows may leave less room for it.

    Default glyph   Status ~
                   added (also untracked files and copies)
                   modified (type changes `T` are shown as modified)
                   deleted
                   renamed
                   ignored
                   staged
                   conflict

A change that is only staged shows its type and the staged check. A worktree
change leaves the second slot blank. When both the index and the worktree have
changes, both types are shown. Untracked files show the added glyph and a
blank slot. Directories combine the status of their contents, separately for
the index and the worktree.

Names and icons are coloured to match the first (leftmost) symbol: the index
status when there is one, otherwise the worktree status. See
|direct.vim-highlights| for the groups.

Change the glyphs with |direct-git.symbols|, or hide the status component with
|direct-git.show_symbols| while keeping the colours.

Deleted files ~
                                                      *direct.vim-git-deleted*
Tracked files that were deleted from disk are shown as protected rows, and so
are directories that contain them. Their names use the colour of their status.
Hide these rows with |direct-git.show_deleted|.

You can expand and collapse deleted rows, run |:DirectRun| or |:DirectGit| on
them, and stage, reset or restore them with `ga`, `gr` and `gc`. Edits, opens,
yanks and pastes on them are ignored.

Showing only changes ~
                                                         *direct.vim-git-view*
`gs` (|:DirectToggleGitStatus|) switches to a view that shows only entries
with a Git status, with every directory expanded. Press it again to return to
the normal listing. |:DirectGitStatus| switches to the view without toggling
it off.

Directories that contain changes stay visible, and their children are filtered
the same way. The view combines with the other filters (|direct.vim-filters|),
and the entries it hides are never treated as deleted. Outside a repository,
or with |direct-git.enabled| off, the view is empty. These commands are
refused while the listing has unsaved edits.

Jumping between changes ~
                                                     *direct.vim-git-navigate*
`]c` and `[c` (|:DirectNextChange| and |:DirectPreviousChange|) move to the
next and previous entry with a Git change, in any listing. They skip ignored
entries, only look at rows currently in the buffer (not collapsed or hidden
ones), and stop at the ends rather than wrapping.

Staging ~

    ga          `git add -- {entry}`
    gr          `git reset -- {entry}`
    gc          `git checkout -- {entry}`

These run through |:DirectGit|, so the status display refreshes when they
finish.

Ignore filtering ~
                                                       *direct.vim-git-ignore*
With |direct-respect_gitignore| on (the default), Git-ignored entries are
hidden. `gi` (|:DirectToggleGitIgnore|) toggles the filter in the current
listing; it is refused while the listing has unsaved edits, and it collapses
expanded directories.

The filter asks Git itself, so it follows root and nested `.gitignore` files,
negations, anchoring, escaped patterns, `.git/info/exclude` and your global
excludes file. Tracked files are never hidden, and neither are directories
that contain tracked files. Outside a repository the filter has no effect.

Git must be installed when the filter is on. If an ignore query fails inside a
repository, the listing fails rather than guessing.

If the ignore rules or the set of tracked files change after a directory is
listed, saving is refused before anything changes. List the directory again to
pick up the new rules. To detect changes, direct.vim currently walks the whole
repository looking for ignore files, so very large repositories take longer to
list and save. A change in a nested repository's ignore file can require a
re-list even when it doesn't affect the current listing.

9. Running commands                                           *direct.vim-run*

|:DirectRun| runs a shell command on the entry under the cursor:
>
    :DirectRun wc -l {}
    :DirectRun open {}
<
Each `{}` is replaced with the shell-escaped absolute path of the entry. Leave
`{}` unquoted, so that paths with spaces stay one argument. The command must
contain `{}`.

The command runs asynchronously, from the listing's directory. Its output and
exit status are shown when it finishes. The current row must be an existing
entry or a deleted tracked file (|direct.vim-git-deleted|).

|:DirectGit| works the same way and also refreshes the Git status in the
listing when the command finishes. It doesn't re-list the directory or change
the buffer text. Successful commands are quiet, and failures show the exit
status and output.
>
    :DirectGit git add -p -- {}
    :DirectGit git restore --staged -- {}
<

10. LSP file operations                                       *direct.vim-lsp*

direct.vim tells language servers about the filesystem changes it makes, so
they can, for example, update imports when a file is renamed. Only servers
that advertise the matching `workspace.fileOperations` capability are
contacted, and their file and glob filters are respected where Neovim exposes
them.

    Event                           When ~
    `workspace/willRenameFiles`       Before a rename. The server can return
                                    edits, such as import updates.
    `workspace/didRenameFiles`        After a rename.
    `workspace/didCreateFiles`        After entries are created or pasted.
    `workspace/didDeleteFiles`        After entries are deleted.

Servers are chosen by whether their workspace covers the paths, not by whether
they are attached to the listing buffer. Paths are sent as `file:` URIs.

Renames ~

The `willRenameFiles` request is asynchronous. |:write| returns straight away,
and the listing stays modified until the servers reply. Other direct.vim
filesystem operations are refused in the meantime.

Edits returned by servers are applied in client-ID order. If a server returns
an error or doesn't reply within the timeout, you get a warning and the rename
goes ahead without that server's edits. If an edit can't be applied, the
rename is refused; edits already applied by other servers are kept. Before
renaming, direct.vim checks the listing and the filesystem again, in case the
edits changed them.

Notifications ~

Notifications are only sent for changes that succeeded, including pastes, undo
and redo. Internal paths (trash, register, temporary and quarantine paths) are
never reported, and yanking on its own sends nothing.

11. Configuration                                           *direct.vim-setup*
                                                              *direct.setup()*
Calling `setup()` is optional. These are the defaults:
>lua
    require('direct').setup({
      map_default_keys = true,
      show_hidden = true,
      respect_gitignore = true,
      indent_size = 2,
      directory_separator = package.config:sub(1, 1),
      max_recursive_expand_depth = false,
      show_folder_icons = true,
      show_file_icons = true,
      show_filetype_icons = true,
      icons = {
        file = '\u{f15b}',
        folder = '\u{f07b}',
        folder_open = '\u{f07c}',
        deleted_file = '\u{f016}',
        deleted_folder = '\u{f114}',
        deleted_folder_open = '\u{f115}',
      },
      git = {
        enabled = true,
        show_symbols = true,
        show_deleted = true,
        symbols = {
          added = '\u{f067}',
          deleted = '\u{f068}',
          modified = '\u{f01f}',
          renamed = '\u{f061}',
          ignored = '\u{f070}',
          staged = '\u{f00c}',
          conflict = '\u{f00d}',
        },
      },
    })
<
You can call `setup()` more than once. Each call replaces the previous options
rather than merging with them. An unknown or invalid option is reported as an
error, and its default is used instead.

                                                     *direct-map_default_keys*
map_default_keys        boolean (default: `true`)
    Install the global `-` mapping and the buffer-local mappings in
    listings. Set to `false` to install none of them. See
    |direct.vim-mappings|.

                                                          *direct-show_hidden*
show_hidden             boolean (default: `true`)
    Show entries whose names start with a dot. `gh` (|:DirectToggleHidden|)
    toggles this in the current listing.

                                                    *direct-respect_gitignore*
respect_gitignore       boolean (default: `true`)
    Hide Git-ignored entries. `gi` (|:DirectToggleGitIgnore|) toggles this in
    the current listing. See |direct.vim-git-ignore|.

                                                          *direct-indent_size*
indent_size             integer (default: `2`)
    Spaces per tree level in expanded directories. Must be greater than 1.

                                                  *direct-directory_separator*
directory_separator     `'/'` or `'\'` (default: the platform separator)
    The trailing marker that identifies directory rows. Set it before
    opening listings. See |direct.vim-separator-rule|.

                                           *direct-max_recursive_expand_depth*
max_recursive_expand_depth   `false` or positive integer (default: `false`)
    The maximum number of levels that `zO`, `zA`, `zR` and
    |:DirectUnfoldAll| expand. `false` means unlimited. One-level `zo` and
    `za` are not affected.

                           *direct-show_folder_icons* *direct-show_file_icons*
show_folder_icons       boolean (default: `true`)
show_file_icons         boolean (default: `true`)
    Show icons before folder and file names. When only one kind is shown,
    the other kind keeps a blank space so the names stay aligned. Icons are
    virtual text, so they don't affect the buffer lines.

                                                  *direct-show_filetype_icons*
show_filetype_icons     boolean (default: `true`)
    Give files the icon and colour for their filetype, from nvim-web-devicons
    (the same lookup bufferline.nvim uses). Without nvim-web-devicons, or for
    a filetype it doesn't know, files use `icons.file`. Set to `false` to use
    `icons.file` for every file. Folders and deleted tracked files keep their
    own icons. Has no effect when |direct-show_file_icons| is off.

                                                                *direct-icons*
icons                   table
    The glyphs used for icons. Any key you leave out keeps its default.
    `file` is used for every file unless |direct-show_filetype_icons| finds
    an icon for its type.

    Key                     Default ~
    `file`                    U+F15B  (file)
    `folder`                  U+F07B  (folder)
    `folder_open`             U+F07C  (open folder)
    `deleted_file`            U+F016  (outlined file)
    `deleted_folder`          U+F114  (outlined folder)
    `deleted_folder_open`     U+F115  (outlined open folder)

    The `deleted_*` icons are used for deleted tracked files
    (|direct.vim-git-deleted|).

                                                          *direct-git.enabled*
git.enabled             boolean (default: `true`)
    Show Git status. Turning this off doesn't affect
    |direct-respect_gitignore|.

                                                     *direct-git.show_symbols*
git.show_symbols        boolean (default: `true`)
    Show the right-aligned status symbols. When `false`, names and icons are
    still coloured and the Git views still work.

                                                     *direct-git.show_deleted*
git.show_deleted        boolean (default: `true`)
    Show rows for deleted tracked files (|direct.vim-git-deleted|). Has no
    effect when |direct-git.enabled| is off.

                                                          *direct-git.symbols*
git.symbols             table
    The status glyphs: `added`, `deleted`, `modified`, `renamed`, `ignored`,
    `staged` and `conflict`. Each one must be a single display cell, or an
    empty string to hide that marker. Keys you leave out keep their defaults.
>lua
    require('direct').setup({
      git = {
        symbols = {
          added = '+', deleted = '-', modified = '~', renamed = '>',
          ignored = 'i', staged = '✓', conflict = '!',
        },
      },
    })
<

12. Highlights                                         *direct.vim-highlights*

Every group links to a standard group by default, so it follows your colour
scheme. Override them in your colour scheme or with |nvim_set_hl()|. The
defaults are applied again after a |ColorScheme| event, but your own
definitions are kept.

    Group                       Used for                      Default link ~
    DirectDirectory             directory names               |hl-Directory|
    DirectHiddenDirectory       hidden directory names        Comment
    DirectHiddenFile            hidden file names             Comment
    DirectFolderIcon            folder icons                  |hl-Directory|
    DirectFileIcon              file icons                    |hl-Normal|
    DirectHiddenFolderIcon      hidden folder icons           Comment
    DirectHiddenFileIcon        hidden file icons             Comment
    DirectGitAdded              added symbol                  Added
    DirectGitDeleted            deleted symbol                Removed
    DirectGitModified           modified symbol               Changed
    DirectGitRenamed            renamed symbol               DirectGitModified
    DirectGitConflict           conflict symbol               |hl-ErrorMsg|
    DirectGitIgnored            ignored symbol                Comment
    DirectGitStaged             staged symbol                 DirectGitAdded
    DirectGitDeletedFile        deleted tracked file names    |hl-ErrorMsg|
    DirectGitDeletedDirectory   deleted tracked dir names     |hl-ErrorMsg|

File names get no highlighting based on their name or type. With
|direct-show_filetype_icons|, file icons use nvim-web-devicons' colour for
their type. Changed entries are coloured by their Git status
(|direct.vim-git-status|).

Listings use their own syntax file, which loads even when Neovim's global
syntax loading is turned off.

13. Commands                                             *direct.vim-commands*

Unless noted otherwise, these commands work only in a listing. In any other
buffer they report an error and do nothing.

Opening listings ~
                                                                 *:DirectList*
:DirectList {dir}
    List {dir}. Completes directory names. Works from any buffer.

                                                           *:DirectListBuffer*
:DirectListBuffer
    List the directory of the current file. In a buffer with no file name,
    or with a non-empty 'buftype', list the working directory instead.
    Works from any buffer.

                                                              *:DirectListCwd*

16. Data and safety                                          *direct.vim-data*

Data directory ~

direct.vim keeps its state in:

    1. `$XDG_DATA_HOME/direct`, when `$XDG_DATA_HOME` is set and not empty;
    2. otherwise `$HOME/.local/share/direct`;
    3. if neither variable is set, Neovim's standard data directory, with a
       warning.

The location is worked out each time it is used. `:checkhealth direct` shows
the current one. It contains:

    `history/`               `undo.log`, `redo.log` and the transaction
                           journal
    `trash/`                 deleted entries, kept so undo can restore them
    `register/`              the latest yank
    `.direct-history.lock`   the lock file shared by Neovim instances

History format ~
                                                   *direct.vim-history-format*
`undo.log` and `redo.log` are JSONL files. Each starts with the header
`{"format":"direct-history","version":1}`, followed by one JSON action per
line. Both files are checked before the register is read or the filesystem is
changed.

A history file that can't be read stops the operation. A file in any other
format (old, newer, damaged or unrecognised) is discarded without a warning,
and both stacks are reset to empty. History is never migrated or backed up.

Crash safety ~

Each history file is rewritten through a new temporary file in the same
directory, which is synced to disk and then renamed over the old file.
Directories are synced too, where the platform supports it. A transaction
journal keeps the undo and redo stacks consistent, and an interrupted rewrite
is finished the next time the history is used.

An undo or redo entry is kept until its filesystem change has succeeded.
Actions are written to the journal before they run: simple changes, the
staging and final renames of grouped moves, and the progress of pastes and
their undo. After a crash, direct.vim uses the recorded identities and
content checks to finish the steps whose outcome is clear, then updates the
history to match. If it can't tell what happened, for example with a partial
copy, a changed quarantine path or a damaged journal, it keeps everything as
it is and refuses further undo and redo until you inspect the paths it
reports.

Locking ~

Neovim instances on the same machine that share a data directory coordinate
through an advisory lock. It is held while direct.vim changes the filesystem
and updates the history, including during asynchronous pastes, undos and
redos. The
operating system releases it if Neovim exits or crashes.

Other programs don't use this lock, so they can still change files while
direct.vim is working. Locking across machines and on network filesystems is
not guaranteed.

Filesystem changes ~

direct.vim never overwrites an existing entry:

    - Moves and renames use the platform's atomic no-replace move (on Linux,
      macOS and Windows). Platforms or filesystems without one are refused.
    - New files are created exclusively, and creating a directory fails if
      the path exists.
    - Symlinks are recreated, not followed. FIFOs, sockets and device files
      can't be moved across filesystems.

Moving across filesystems ~
                                                            *direct.vim-exdev*
A move to another filesystem is done as a copy. The file or tree is copied to
a temporary path in the destination directory, then renamed into place
without replacing anything.

Before the original is removed, it is moved to a temporary directory next to
it and compared with the copy. If it changed or can't be checked, it is put
back, or its temporary path is reported, rather than deleted. A crash at this
point can leave a `.direct-exdev-source-*` directory to recover. If the copy
is in place but the original can't be removed, both paths are reported and two
copies may remain.

Limits: a program that has a file open can still change it after the
comparison. A process run by the same user could swap a path between a check
and the next step; if that happens, direct.vim keeps the temporary path and
reports it so you can recover it. Network filesystems are not guaranteed.

17. Upgrading from the Python version                     *direct.vim-upgrade*

The Lua version uses a new data format and doesn't migrate the Python
version's data:

    - History: old history is discarded and replaced with empty stacks,
      without migration or backup. A history file that can't be read still
      blocks operations.
    - Register: entries yanked with the Python version still appear. Names
      with spaces are supported. Names with control characters or invalid
      UTF-8 are skipped with an error.
    - Trash: entries deleted with the Python version can still be restored.
